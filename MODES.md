# MODES — режимы работы, доступ, устойчивость Monolog

Рабочий документ. Дополняется по ходу. Версия 0.1 (2026-09-17).

---

## 1. Режимы работы

Пять режимов. Переключаются в UI и командой в чате.

| Режим | Кто решает | Кто действует | Когда |
|---|---|---|---|
| **AUTO** | Monolog | Monolog | Промпты стабильны, задача простая |
| **CONFIRM** | Monolog предлагает | Monolog после подтверждения | Промпты нестабильны, риск средний |
| **MANUAL** | Пользователь | Monolog по команде | Полный контроль |
| **RAW** | Пользователь | Monolog сохраняет, не анализирует | Вставка кода вручную |
| **OFF** | — | Никто | Monolog спит |

По умолчанию — **CONFIRM**. Потому что промпты ещё нестабильны.

**Переключение:**

- В интерфейсе — селектор режима.
- В чате — командой: «режим авто», «режим подтверждение», «режим ручной», «режим raw», «режим off».

Каждое действие Monolog знает, в каком режиме работает.

## 2. Инструменты (внутренние)

Доступны, когда backend работает.

| Эндпоинт | Что делает |
|---|---|
| `POST /chat` | общение |
| `POST /ai/apply` | сохранить файл (JSON body) |
| `POST /ai/apply_raw` | сохранить файл (text/plain body) |
| `GET /code/read` | прочитать файл |
| `POST /code/save` | сохранить в ветку CODE_BRANCH |
| `GET /code/check` | проверить синтаксис одного файла |
| `GET /code/diagnose` | проверить все .py файлы |
| `GET /public/*` | публичные данные |

Плюс будущие:

- `POST /code/copy_branch` — копировать main → dev или наоборот.
- `POST /code/create_branch` — создать новую ветку.
- `GET /code/export` — выгрузить репо как zip.

---

## 3. Аварийный доступ (внешний)

Когда backend не запускается — внутренние инструменты недоступны.

Внешние точки доступа:

1. **GitHub-веб** — работает всегда. Но искажает файлы >80 строк. Значит: только для коротких правок.
2. **Второй сервис** — если `main` сломан, работаем из `dev`. Если `dev` сломан — из `main`. Симметрично.

Внешний редактор (codesandbox, gitpod) — **не используем**.

---

## 4. Два сервиса: main и dev

Оба на Render. Оба подключены к одному репозиторию, но разным веткам.

| Сервис | Ветка | URL |
|---|---|---|
| ai-monolog | main | ai-monolog.onrender.com |
| agent-23r6 | dev | agent-23r6.onrender.com |

**Взаимное управление:**

- Из main-сервиса можно писать в ветку `dev` (через `CODE_BRANCH=dev`).
- Из dev-сервиса можно писать в ветку `main` (через `CODE_BRANCH=main`).
- Это реализуется через GitHub API с параметром `ref`.

**Сценарий восстановления:**

1. main сломан.
2. Заходим на dev-сервис (agent-23r6).
3. Через dev-сервис читаем / пишем в ветку `main`.
4. Исправляем код.
5. Render передеплоит main.
6. main оживает.

Симметрично — наоборот.

## 5. Выгрузка репозитория

**Зачем:**

- Бэкап перед опасными изменениями.
- Переезд на другой хостинг.
- Восстановление.

**Что нужно:**

- `GET /code/export` — упаковать всё содержимое репо в zip.
- `POST /code/copy_branch` — скопировать одну ветку в другую.
- `POST /code/create_branch` — создать новую ветку.

**Через GitHub API** это реализуется: есть эндпоинты tree, contents, git/refs.

---

## 6. Создание веток

**Зачем:**

- Для экспериментов, не трогая main.
- Для тестов.
- Для временных правок.

**Как:**

- `POST /code/create_branch` — параметры: `name` (имя ветки), `from_branch` (опционально, по умолчанию main).
- Или через GitHub-веб — вручную.
- Ветка создаётся как копия base-ветки.

**Что даёт:**

- Можно экспериментировать без риска.
- Можно вернуться к стабильному main.
- Можно параллельно разрабатывать разные фичи.

---

## 7. Правила устойчивости

Чтобы система не падала целиком:

- **`app.py` ≤ 100 строк** — чтобы всегда можно было перезалить через GitHub-веб.
- **Роутеры ≤ 200 строк** — чтобы GitHub-веб не искажал.
- **Все модули автономны** — падение одного не блокирует остальные.
- **`APP_MODE=stub`** — всегда доступен как спасатель.
- **`storage`** — с локальной опцией (когда появится), если GitHub недоступен.
- **Два сервиса** — main и dev — взаимная страховка.
- **Коммит после каждого действия** — можно откатиться по истории.

## 8. Роли

**Пользователь:**

- Ставит задачу.
- Выбирает режим.
- Подтверждает (в CONFIRM).
- Видит результат.
- Может вмешаться в любой момент.
- Дополняет документы по ходу.

**Monolog:**

- Планирует.
- Выполняет через инструменты.
- Проверяет результат.
- Откатывает при ошибке.
- Отчитывается пользователю.
- Может запросить подтверждение, если не уверен.

**Внешние инструменты:**

- GitHub-веб — аварийный доступ.
- Второй сервис (main или dev) — взаимное управление.
- Локальный git — если есть компьютер (будущее).
